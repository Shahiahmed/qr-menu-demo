# Qmenu — QR-меню для ресторанов

> **Правило для этого файла:** он обновляется каждый раз, когда в проекте
> появляется что-то новое — раздел, компонент, роут, таблица, зависимость или
> найденные грабли. Внизу — «Журнал изменений», новые записи добавляются
> сверху. Читать этот файл первым, до кода.

---

## 1. Что это за проект

Мультитенантный SaaS «QR-меню для ресторанов и кафе». Рынок — Казахстан.

Гость сканирует QR-код на столе → открывает меню заведения в браузере без
установки приложения → может сделать заказ прямо со стола. Заведение через
админку ведёт меню, цены, стоп-лист и получает уведомления о заказах.

Ключевые требования домена:

- **Двуязычность.** Все тексты меню в двух вариантах: `name_ru` / `name_kz`,
  `description_ru` / `description_kz`. Гость выбирает язык сам.
- **Деньги в тенге (₸)**, хранить в минорных единицах (`int`, тиыны).
  Не использовать float.
- **Мультитенантность через колонку `tenant_id`** (на старте — не отдельные
  схемы). Любой запрос к данным заведения ОБЯЗАТЕЛЬНО скоупится по `tenant_id`.
- **Публичное меню read-heavy** — кэшировать отрендеренные данные,
  инвалидировать кэш при любом редактировании меню.

## 4. Текущее состояние

**Готово:** только публичный лендинг (маркетинговая страница).

**Бэкенд:** поднят API-слой и авторизация — регистрация, вход, выход,
`/api/user`. Sanctum в SPA-режиме (куки). 15 тестов на Pest, все зелёные.

**Фронт авторизации:** `/[locale]/register`, `/login`, `/dashboard`
(заглушка). API-клиент `src/lib/api.ts` — куки, CSRF, разбор ошибок 422.
Фетчинг через TanStack Query.

**Заведения (тенанты).** Таблица `establishments` — это и есть тенант: меню,
категории, блюда и заказы будут нести `establishment_id` и скоупиться по нему.
Один владелец может держать несколько точек (заложено сразу — в Премиуме это
продаётся). CRUD через `/api/establishments`, кабинет с вкладками
«Заведения» / «Профиль».

**Меню.** Таблицы `menu_categories` и `dishes` (двуязычные поля, цена в
тиынах, стоп-лист). Редактор на `/dashboard/venues/[id]/menu`: разделы,
блюда, стоп-лист и скрытие от гостей в один тап (оптимистично). Новое
заведение получает стартовый шаблон; пустое — кнопка «Заполнить примером».

**Публичное меню гостя.** `/m/{slug}` — то, что открывается по QR-коду.
Без авторизации, кэшируется целиком на сутки, сбрасывается при любой правке.
Переключатель RU/KZ внутри страницы, откат на русский для непереведённого.
**Нижнее меню-навбар** (Меню · Корзина · Настройки; «Корзина» — только когда
включён заказ, т.е. на демо). В «Настройках» **сам гость** выбирает цвет (8 тем)
и дизайн раскладки (3 варианта) — выбор владельца в «Оформлении» остаётся лишь
**значением по умолчанию**, гость его переопределяет; выбор гостя хранится в
`localStorage` по слагу (`src/lib/guestPrefs.ts`), не трогая данные заведения.

**QR-код.** `/dashboard/venues/[id]/qr` — настоящий сканируемый код на URL
меню, скачивание PNG/SVG, печатная табличка на стол. **Конструктор:** владелец
меняет форму точек (5 пресетов) и углов (3), цвет кода и фон (готовые палитры +
свои цвета через `<input type=color>`), вставляет **логотип** в центр (свой
файлом или логотип заведения) — живой предпросмотр, потом скачивает. Логотип
поднимает коррекцию ошибок до `H`. Рисует библиотека `qr-code-styling` (старый
`qrcode` умел только цвет + уровень коррекции, без логотипа — см. §7).

**Картинки заведения.** Обложка и логотип грузятся в конструкторе
(«Оформление»). **Фото блюд** — в диалоге блюда: владелец выбирает файл,
**кадрирует квадрат** (пан/зум) в браузере, клиент отдаёт готовый WebP ~800px,
бэк для надёжности ре-кропит квадрат ещё раз (GD). Всё ужимается в WebP, URL
строится из пути. Логотип рисуется по центру обложки в гостевом меню, фото
блюда — миниатюрой в карточке и корзине.

**Хранилище картинок — одна папка на заведение.** Всё имущество заведения
лежит под `storage/app/public/venues/{id}-{slug}/`: `cover/`, `logo/`,
`dishes/{id}/`. Папка заводится при создании заведения; переименование двигает
всю папку и переписывает пути (см. §7).

**Админка (Filament).** `/admin` — панель для сотрудников платформы, отдельная
от кабинета владельца. Blade/Livewire на сессии `web` (не Sanctum). Дашборд со
статистикой, модерация заведений (+ ссылка на живое меню гостя) и пользователей.
Доступ — по флагу `is_admin` на юзере; выдаётся командой `php artisan admin:grant`.
На дашборде есть виджет **«Обслуживание»** (`MaintenanceCommands`): живой статус
(миграции / симлинк storage / тарифы / GD WebP) и кнопки для ручных команд
деплоя — `migrate --force`, `storage:link`, `optimize:clear`, засев тарифов.
Команды из **фиксированного белого списка** (никакого произвольного ввода),
каждая перепроверяет `is_admin`; «Засеять тарифы» показывается только на пустом
каталоге — см. §7.

**Подписки.** Тарифы (`plans`) заводит и правит админ в `/admin` (цена в
тиынах, скидка %, период месяц/год, двуязычные название/подзаголовок/список
возможностей, флаги активности и «популярный», лимит заведений). Владелец в
кабинете (`/dashboard/subscription`) видит **каждое своё меню отдельно** и
оставляет **заявку на конкретное меню** (`subscription_requests`, несёт
`establishment_id`) — онлайн-оплаты нет, активация ручная: админ в панели
«Заявки на подписку» жмёт «Одобрить» → создаётся `subscriptions` (тоже несёт
`establishment_id`) через `SubscriptionService`. Лендинг тянет тарифы из БД
(`GET /api/plans`, кэш сутки) с откатом на статичную копию. **v1 только
фиксирует тариф — гейтинг (реальное ограничение по тарифу) сознательно
отложен.** Тарифы различаются **только сроком доступа одного меню** (биллинг
per-menu, тарифа «безлимит меню» больше нет). Дефолтные — в `PlanSeeder`
(Бесплатный 1 мес · На 6 месяцев 15 000 ₸ · На год 25 000 ₸, featured; цены —
плейсхолдеры, правятся в `/admin`), запускается **вручную** на сервере, не в
`deploy.sh` (иначе затрёт правки цен из админки).

**Подписка — на каждое меню отдельно (per-menu).** Заявка и подписка привязаны
к `establishment_id`; окно доступа меню считается по **его собственной**
активной подписке, а не по владельцу. Оплата одного меню не продлевает
соседние. Раньше подписка была на весь аккаунт (`User::currentSubscription`) —
это давало соседнему меню чужой год; переделано на per-menu (см. журнал
2026-07-29). Одобрение закрывает предыдущую активную подписку **того же меню**
(retire scoped по `establishment_id`) и сбрасывает кэш **только этого** меню.
Одна открытая заявка **на меню** (409 при повторной на то же меню; на другое —
можно).

**Срок доступа меню (access window).** У каждого меню есть срок, после которого
гостевой `/m/{slug}` отдаёт 404. Логика: новое заведение получает **пробную
неделю** (`establishments.trial_ends_at`, `TRIAL_DAYS = 7`, ставится событием
`creating`). **Активная подписка этого меню перекрывает** пробный период — её
`ends_at` (месяц для free-тарифа, год для платного, см. `SubscriptionService`)
становится сроком доступа. `Establishment::accessEndsAt/accessSource/isExpired/
daysLeft` считают эффективный срок по `Establishment::currentSubscription`
(HasOne на **своё** меню); проверка на 404 — **живая** в
`PublicMenuController` (сравнение запечённого `access_ends_at` с `now()` на
каждый запрос). Владелец видит обратный отсчёт в кабинете (карточки заведений
+ вкладка «Подписка», список меню), админ — колонку «Доступ» в «Заведениях»,
колонку «Меню» в «Заявках»/«Подписках» и раздел «Подписки» (создаются только
одобрением заявки, но админ может вручную **изменить** статус/дату окончания
или **удалить** — ручной override, см. §7).
Заведения без `trial_ends_at` (созданные до фичи) — **бессрочные**
(grandfathered, `null` = без ограничений).

**SEO из админки.** Метаданные лендинга правятся в `/admin` → «SEO»
(синглтон `seo_settings`): двуязычные title/description/keywords, OG-картинка,
канонический домен. Публичный `GET /api/seo` (кэш сутки, сброс на
`saved`); фронт читает серверным `getSeo()` в `generateMetadata`/`robots`/
`sitemap` с ISR ~1 час и откатом на `content/landing.ts`. Лендинг из-за этого
перешёл с `force-static` на `revalidate = 3600` (см. журнал 2026-07-30).
**Тумблера `noindex` нет намеренно** — лендинг всегда индексируется, чтобы
случайный клик в админке не спрятал живой сайт из поиска (см. журнал 2026-07-30).

**Реферальная программа.** Двусторонние скидки-деньги (не бесплатные месяцы):
пригласивший +10 000 ₸ при первой платной оплате друга, приглашённый +5 000 ₸
сразу при регистрации по ссылке. Копятся в кошельке `users.referral_credit`
(тиын), тратятся при оформлении подписки. Раздел кабинета
`/dashboard/referral` (ссылка, код, шэр, баланс, счётчики, кто пригласил).
Суммы и вкл/выкл — в `/admin` (`ReferralSetting`). Реф-поля/леджер не fillable,
пишет только `ReferralService`. Подробности и ⚠️ ручные шаги — журнал 2026-08-28.

**Не начато:** гейтинг возможностей по тарифу, приём заказов на сервере
(сейчас только локальный чек на телефоне гостя), вызов официанта, чаевые через
Kaspi, аналитика, коды на каждый стол.

Детали лендинга:

- Рендер статический: `export const dynamic = "force-static"` в `page.tsx`.
- **Язык в URL:** `/ru` и `/kz` — отдельные статические страницы. Локаль
  приходит из сегмента `[locale]`, `LandingLocaleProvider` только раздаёт её
  вниз. Переключатель языка — это `<Link>`, то есть навигация, не стейт.
- Тексты не хардкодятся в компонентах — всё в `src/content/landing.ts`,
  типизировано через `LandingCopy`. **Добавляя строку на лендинг, добавь ключ
  в тип и в обе локали (RU и KZ)**, иначе TypeScript не соберётся.

## 6. Конвенции

**Общие**
- Код и комментарии — **на английском**. UI-тексты — русский + казахский.
- Комментарий объясняет *почему*, а не *что*. Не дублировать код словами.

**Бэкенд**
- Eloquent: всегда eager loading (`with()`), никаких N+1.
- Индексы на `tenant_id` и все внешние ключи — обязательны.
- Ответы только через API-ресурсы (`JsonResource`), не отдавать модели напрямую.
- Валидация — через Form Request классы.
- Тесты на ключевую бизнес-логику (Pest).

**Фронт**
- Мобайл-фёрст для всех гостевых экранов.
- Дизайн-токены живут в `globals.css` (`:root` + `@theme inline`). Не хардкодить
  цвета в компонентах — использовать `text-accent`, `bg-surface` и т.п.
- Секции оборачиваются в `<Reveal>` для появления при скролле; анимации
  отключаются через `prefers-reduced-motion`.
- Картинки при загрузке ужимать в WebP + ресайз, отдавать через CDN.

## 7. Грабли (проверено на практике)

### ⚠️ `hidden` не работает на `<Button>`

`Button` в `baseClasses` жёстко задаёт `inline-flex`. Если передать
`className="hidden sm:inline-flex"`, оба класса попадают в один CSS-слой
`display`, и в сгенерированном Tailwind-файле `inline-flex` идёт **после**
`hidden` — побеждает он. Порядок классов в атрибуте роли не играет.

Кнопка остаётся видимой на всех ширинах и разрывает вёрстку.

```tsx
// ❌ не сработает
<Button className="hidden sm:inline-flex">Войти</Button>

// ✅ адаптивность на обёртке
<span className="hidden sm:inline-flex">
  <Button>Войти</Button>
</span>
```

То же касается любого утилити-класса, который уже задан в `baseClasses`
(`px-*`, `py-*`, `rounded-*`). Проверять при конфликте.

### ⚠️ Два разных «QR» в проекте — не перепутать

`components/landing/ui/QrCode.tsx` — **декоративный**: узор из хэша для
макета телефона на лендинге. Не сканируется, и не должен.

`components/panel/VenueQr.tsx` — **настоящий**, конструктор на библиотеке
`qr-code-styling` (не `qrcode`), кодирует реальный URL меню. Уровень коррекции
`M` (~15% повреждений) без логотипа — компромисс для таблички, которую заляпают
на столе; с логотипом поднимается до `H`, иначе картинка в центре съест данные
и код не прочтётся.

URL берётся из `window.location.origin`, а не из константы: иначе на
превью-деплое или своём домене напечатанные коды поведут не туда.

### ⚠️ `qr-code-styling`: DOM-only, чистка логотипа, экспорт SVG, кросс-ориджин

Грабли конструктора QR (`VenueQr.tsx`), проверенные при интеграции:

- **Только браузер.** Библиотека трогает `window`/`document` при создании
  инстанса. Импорт на верхнем уровне `"use client"`-модуля роняет
  SSR-пререндер в `next build` — поэтому `import("qr-code-styling")` **внутри
  `useEffect`**, инстанс живёт в `useRef`.
- **Убрать логотип = `image: ""`, не `undefined`.** `update()` **мёржит**
  опции, поэтому `undefined` оставит старую картинку. Библиотека рисует лого
  за `if (options.image)` — пустая строка (falsy) надёжно очищает.
- **SVG-экспорт — отдельный инстанс.** Предпросмотр рисуется в `canvas`
  (чёткий + PNG-скачивание/печать), а canvas **не отдаёт вектор**. Кнопка
  «Скачать SVG» создаёт временный инстанс с `type: "svg"` и зовёт `download`.
- **Печатная табличка — `<img>` из PNG-даты**, не сам canvas: живой canvas при
  печати в некоторых браузерах выходит пустым. PNG берётся `getRawData("png")`
  → objectURL (ревокается при смене опций).
- **Логотип заведения — через свой прокси, не прямым `fetch`.** `logo_url`
  живёт на `api.qmenu.kz` (кросс-ориджин); чтение напрямую требует CORS на
  `/storage` (у статики nginx его нет) → canvas «портится», экспорт падает.
  Поэтому «Логотип заведения» грузится через same-origin route handler
  `app/api/venue-logo` (сервер тянет картинку, отдаёт со своего origin) —
  браузер видит same-origin и растеризует свободно. Прокси **только** для
  нашего API-хоста (проверка `origin`, не открытый прокси). `try/catch` всё
  равно оставлен — при сбое показываем подсказку. **Загрузка своего файла**
  (FileReader → dataURL) работает всегда, без прокси.
  ⚠️ `proxy.ts` matcher обязан исключать `api` (`(?!_next|api|...)`), иначе
  `/api/*` уедет под локаль-редирект (`/ru/api/...`) и роут не ответит.

### ⚠️ Кэш публичного меню сбрасывается через события моделей

`PublicMenu` кэширует ответ целиком на сутки. Инвалидация висит на событиях
моделей (`InvalidatesPublicMenu` + `booted` у `Establishment`), а **не** в
контроллерах: иначе консольная команда или новый эндпоинт оставят гостю
цену, которую никто не берёт, и никто об этом не узнает.

Переименование заведения чистит и **старый** slug — иначе он продолжит
отвечать после переезда адреса.

### ⚠️ Картинки: WebP через GD, путь в БД, нужен symlink

`VenueImage` ужимает загрузку в **WebP через GD** (`imagecreatefromstring` →
`imagecopyresampled` → `imagewebp`), а не хранит сырое фото с телефона. Значит,
на сервере обязателен `php8.3-gd` **с поддержкой WebP** (проверка:
`gd_info()['WebP Support']`) — иначе `imagewebp` фатально падает.

В колонках лежит **относительный путь** (`venues/{id}/cover-….webp`), а не URL:
абсолютный URL строится в ресурсе из `Storage::disk('public')->url()` (берёт
`APP_URL`). Поэтому нужен симлинк `public/storage` — его ставит `deploy.sh`
(`artisan storage:link`). Без симлинка картинки отдают 404.

`cover_path`/`logo_path` **в `#[Fillable]`**, потому что `VenueImage` пишет их
через `->update()` (чтобы `saved` сбросил кэш меню) — без fillable апдейт молча
проглотит колонку. При этом в `UpdateEstablishmentRequest` их нет: ставит их
только загрузчик, не форма.

Имя файла рандомное на каждую загрузку — новый URL сам инвалидирует кэш
браузера/CDN; старый файл при замене удаляется.

### ⚠️ Одна папка на заведение, переименование двигает её целиком

Путь картинки строится от `Establishment::storageFolder()` =
`venues/{id}-{slug}` (id — чтобы стабильно и без коллизий, slug — чтобы
по-человечески читалось в файлах). Внутри — `cover/`, `logo/`, `dishes/{id}/`.
Папка создаётся событием `created`.

При смене слага **весь путь папки меняется**. Чтобы файлы заведения не
разъехались по старой и новой папке, событие `updating` двигает всю папку
(`@rename` по абсолютному пути локального диска) и переписывает **все**
запечённые пути: `cover_path`/`logo_path` — в самой модели (мутируются перед
записью, едут той же `save`), а `dishes.image_path` — прямым `update()` по
таблице (без событий: кэш меню и так сбрасывается этим же сохранением). Пути
в БД **относительные**, поэтому это простой `Str::replaceStart` префикса.
Завязано на **локальный** диск (`Storage::path()` + `rename`) — при переезде
на S3 переписать на пофайловый move.

Фото блюда лежит под папкой **своего** заведения (`$dish->establishment->
storageFolder()`), не в глобальном `dishes/` — иначе одна папка на заведение
рассыпалась бы.

### ⚠️ Гостевое меню живёт вне языковых префиксов

`/m/{slug}`, не `/ru/m/...`: адрес печатается на табличке, должен быть
коротким и неизменным, а язык гость выбирает внутри. В `proxy.ts` для `/m`
редирект отключён — не сломать при правках локалей.

У этой ветки **свой корневой layout** (`app/m/layout.tsx`), потому что
`app/[locale]/layout.tsx` ей не родитель.

### ⚠️ `export const revalidate` должен быть литералом

Next читает сегментные конфиги статически. `export const revalidate = MY_CONST`
роняет сборку с «Invalid segment configuration export detected».

### ⚠️ Двуязычные колонки — суффикс `kk`, не `kz`

Колонки: `name_ru` / `name_kk`, `description_ru` / `description_kk`.
`.cursorrules` пишет `name_kz`, но `default_locale` заведения хранит `kk`,
и с `_kz` пришлось бы городить маппинг на каждом обращении. С `_kk` работает
просто `"name_{$locale}"`. Казахские поля **nullable** — заведение может
стартовать на русском и перевести позже.

### ⚠️ Цена — только целые тиыны

`dishes.price` — `unsignedBigInteger` в минорных единицах (1/100 ₸).
Никаких float: 2490.00 ₸ не представим точно в двоичной системе, и дрейф
округления вылезет в счёте. Конвертация на границе — `src/lib/money.ts`
(`toMinorUnits` / `formatPrice`), владелец вводит тенге.

### ⚠️ Стоп-лист обязан быть оптимистичным

Ждать ответа сервера — 2-3 секунды до смены строки даже локально
(`artisan serve` однопоточный). Это фича «в один тап», официант жмёт её в
зале на слабом wifi. `onMutate` правит кэш сразу, `onError` откатывает.

### ⚠️ Слаг заведения: уникален глобально и есть запрещённый список

Слаг попадает в публичный URL меню, поэтому уникален по всему сервису, а не
внутри владельца. Плюс `Establishment::RESERVED_SLUGS` — иначе заведение с
именем `api`, `ru` или `login` перекрыло бы роут приложения.

Регистр **нормализуется**, а не отбивается: «Vostok» → `vostok`.

Транслитерация с кириллицы обязательна (`src/lib/slug.ts` на фронте): без неё
«Восточный дворик» превращается в пустую строку. Казахские буквы (ә, ғ, қ, ң,
ө, ұ, ү, һ, і) идут в таблице раньше русских — иначе они схлопнутся в базовую.

### ⚠️ Подписка активируется только из доверенного контекста

`Subscription` (пустой `#[Fillable]`), `SubscriptionRequest.status` и
`reviewed_*` — **не** mass-assignable, как и `is_admin`. Ни один HTTP-путь не
должен уметь выдать себе активную подписку или сменить статус чужой заявки.
Пишет их только `SubscriptionService::approve/reject` — через `forceCreate` /
`forceFill()->save()` внутри `DB::transaction`. Владелец через API только
**создаёт** заявку (`status` берётся из дефолта модели `STATUS_NEW`), решение
принимает админ в панели. Второй `POST` при висящей заявке **на то же меню** →
**409** (одна активная заявка **на меню**, не на владельца — см. ниже per-menu).

`establishment_id` заявки валидируется как **своё** меню:
`Rule::exists('establishments','id')->where('user_id', $this->user()->id)` —
чужое меню отбивается 422, а не даёт оформить подписку соседу.

**Ручной override в `/admin` → «Подписки».** Раздел был read-only, но по запросу
владельца добавлены экшены **«Изменить»** (статус + `ends_at`) и **«Удалить»**
(+ bulk). Это доверенный контекст (панель гейтится `is_admin`), поэтому
`status`/`ends_at` пишутся через **`forceFill()->save()`** — тот же приём, что
у тумблера `is_admin` в `EditUser`. Обычный Filament-EditAction молча ничего не
сохранил бы: `#[Fillable]` у `Subscription` пуст. HTTP-путей к этим экшенам нет
— только панель. `Subscription` подключил трейт `InvalidatesPublicMenu`, чтобы
правка/удаление **сбросили кэш гостевого меню** (иначе снятая подписка держала
бы меню открытым до суток — окно запечено в payload). Смена статуса на «Закрыта»
или дата в прошлом убирают подписку из `currentSubscription` (фильтр
`status=active`) → доступ откатывается на пробный/бессрочный.

### ⚠️ Срок доступа меню: `trial_ends_at` не fillable, проверка живая

`establishments.trial_ends_at` ставится **только событием `creating`** (не в
`#[Fillable]`) — владелец не должен уметь продлить себе пробный период через
форму. Меняет его лишь доверенный код.

Эффективный срок доступа = `Establishment::accessEndsAt()`: если у **этого
меню** есть **активная подписка** (`Establishment::currentSubscription`, `HasOne`
с `latestOfMany` — подписка **своего** меню, не владельца) — её `ends_at`, иначе
— `trial_ends_at`. Подписка перекрывает пробный период; `null` (нет ни того, ни
другого) = **бессрочно** (grandfathered — заведения, созданные до фичи).
**Подписка per-menu:** оплата одного меню не трогает окно соседнего (раньше
было по владельцу — соседнее меню наследовало чужой год, это баг, переделано).

Гейт 404 в `PublicMenuController` — **живой**, не запечённый: payload
кэшируется на сутки, но `access_ends_at` (абсолютный timestamp) сравнивается с
`now()` на **каждый** запрос. Иначе меню осталось бы открытым до конца
суточного кэша после того, как срок истёк внутри этих суток. При одобрении
подписки `SubscriptionService` **сбрасывает кэш именно этого меню**
(`PublicMenu::forget($establishment->slug)`) — иначе уже погасшее меню не ожило
бы, пока кэш не протухнет сам.

`accessEndsAt/accessSource/isExpired/daysLeft` берут
`Establishment::currentSubscription` из **eager-загруженной** связи
(`with('currentSubscription')` в `EstablishmentController@index`,
`PublicMenu::build`, Filament-таблице) — иначе N+1 на списке заведений.

### ⚠️ Цена тарифа в Filament-форме: тиыны ↔ тенге на границе

`plans.price` хранится в тиынах, но админ вводит тенге. В `PlanForm` поле
`price` конвертит на входе/выходе: `formatStateUsing` делит на 100 при показе,
`dehydrateStateUsing` умножает на 100 при сохранении. Не убирать — иначе цена
уедет в ×100 (см. общий запрет на float для денег ниже).

### ⚠️ Filament: `modifyQueryUsing` с eager-load роняет рендер таблицы

В `SubscriptionRequestsTable` стоял
`->modifyQueryUsing(fn (Builder $q) => $q->with(['user', 'plan']))`, чтобы
подтянуть связи для колонок `user.name` / `plan.name_ru`. Панель падала на
рендере: `Call to a member function newQueryWithoutRelationships() on null`.

Причина: `index.blade.php` **безусловно** зовёт `getAllTableSummaryQuery()` на
каждый рендер → `applyFiltersToTableQuery()` → `where(Closure)` по запросу без
модели, и наша замыкающая модификация возвращала билдер, у которого в этом
контексте модель резолвилась в `null`. Filament **сам** eager-грузит связи для
колонок вида `relation.column` — ручной `with()` тут не нужен и вреден.
**Решение — убрать `modifyQueryUsing` целиком.** Ловится только рендером
(`Livewire::test(Page)`), не юнит-логикой.

### ⚠️ Filament: тест таблицы ищет строку в текущем фильтре

`SubscriptionRequestsTable` дефолтит `SelectFilter('status')` на `new`.
Одобренной заявки в отфильтрованной таблице нет, и `assertActionHidden` роняет
`Record [N] no longer exists`. Перед проверкой нужно переключить фильтр:
`->filterTable('status', SubscriptionRequest::STATUS_APPROVED)`.

### ⚠️ Виджет «Обслуживание» гонит только белый список команд

`MaintenanceCommands` запускает артизан из веб-панели — это по определению
чувствительно. Правила, которые нельзя ослаблять:

- Только **захардкоженные** команды (`migrate --force`, `storage:link`,
  `optimize:clear`, `db:seed --class=PlanSeeder`). **Никакого поля ввода**
  команды/аргументов от пользователя в `Artisan::call()` — иначе это RCE.
- Каждый публичный метод-экшен перепроверяет `abort_unless($user->is_admin)`
  (defense in depth поверх гейта панели) — Livewire-методы вызываемы, пока
  компонент смонтирован.
- **Засев тарифов — кнопка видна всегда, но при непустом каталоге предупреждает.**
  `PlanSeeder` идемпотентен через `updateOrCreate` и **перезапишет цены**
  дефолтных тарифов, отредактированные админом в «Тарифах» (тот же риск, что и
  автозапуск сидера в `deploy.sh`, см. §11). Поэтому `canSeedPlans()` (пусто ли)
  теперь лишь выбирает текст `wire:confirm`: на пустом — обычный, на непустом —
  громкое «цены слетят, продолжить?». Само действие выполняется в любом случае —
  это сознательный ручной сброс к дефолтам.
- Подтверждения — через нативный `wire:confirm`, не Filament-экшены: экшены на
  голом `Widget` требуют трейта `ResolvesDynamicLivewireProperties`, `wire:click`
  проще и надёжнее.

### ⚠️ Общие сообщения валидации врут про другое поле

Правило `unique` срабатывает на нескольких полях. Одно общее сообщение
«Этот email уже зарегистрирован» показывалось при занятом **слаге**. Общий
текст держать нейтральным, конкретику — в `custom.<field>.<rule>`.
Тесты этого не ловят, если проверяют только наличие ключа ошибки.

### ⚠️ Очистка кэша сессии срабатывает как «гость»

У страницы кабинета есть страж: нет пользователя → редирект на `/login`.
Выход очищает кэш (`setAuthUser(null)`), и страж принимал это за приход без
сессии — уводил на вход вместо главной. Гонка. Страж отключается на время
выхода через `signOut.isPending || signOut.isSuccess`.

Ловится только браузерным прогоном — юнит-тест такого не покажет.

### ⚠️ Sanctum: без заголовка `Origin` нет сессии

Sanctum поднимает сессию только для запросов, чей `Origin` есть в
`SANCTUM_STATEFUL_DOMAINS`. Без заголовка он считает вызов токен-API, и
`$request->session()` падает с `Session store not set on request`.

Поэтому `tests/Pest.php` подставляет `Origin` в каждый Feature-тест, а
`phpunit.xml` задаёт `SANCTUM_STATEFUL_DOMAINS`. Тем же объясняются 419-е
от curl без `Origin`.

### ⚠️ `actingAs` не годится для проверки logout

В тестах Laravel переиспользует один экземпляр приложения, поэтому guard
держит пользователя в памяти между запросами. После `actingAs` + logout
`auth()->check()` вернёт `true`, хотя сессия уже пуста — это артефакт
окружения, не баг. Проверять надо через реальные эндпоинты и, при
необходимости, `$this->app['auth']->forgetGuards()`.

### ⚠️ Laravel 13: атрибуты вместо свойств модели

`User` объявляет `#[Fillable([...])]` и `#[Hidden([...])]` над классом, а не
привычные `protected $fillable`. Добавляя поля — править атрибут.

### ⚠️ Next.js 16 ≠ привычный Next.js

`front/AGENTS.md` предупреждает: в этой версии ломающие изменения в API и
структуре файлов. Перед написанием кода читать
`node_modules/next/dist/docs/`, а не полагаться на память.

### ⚠️ Кастомный 404 — через `global-not-found.js`, обычный `not-found.js` не годится

У сайта **нет единого root layout**: страницы под верхним динамическим сегментом
`[locale]`, а `/m` — отдельный корень (каждый сам рендерит `<html>`). Из такой
структуры обычный `app/not-found.js` собрать нельзя — несуществующий URL
(`/kz/asdasd`) отдавал **дефолтный** экран Next. Правильный инструмент (Next 16):
`experimental.globalNotFound: true` в `next.config.ts` + `app/global-not-found.tsx`.
Файл **минует все layout'ы**, поэтому обязан рендерить **свой полный `<html>`** и
сам импортировать `globals.css` + шрифт. Это ровно тот кейс, который docs
(`.../file-conventions/not-found.md`) называют «top-level dynamic segment /
multiple root layouts». **Не путать** с гостевым 404 (`/m/{slug}`) — тот рисуется
инлайн в самой странице (меню не найдено / истекло), не через `notFound()`.

### ⚠️ Вкладки категорий в GuestMenu — не hash + IntersectionObserver

Короткие нижние разделы (напитки) не доезжают до observer-зоны под sticky-
шапкой: клик подсвечивает вкладку, а scroll-spy сразу откатывает на предыдущую.
Нужен явный `scrollTo` с `header.offsetHeight`, короткий lock после клика и
spy по `getBoundingClientRect`, плюс `min-h` у последнего раздела.

### ⚠️ Казахский текст длиннее русского

`«Тегін көріп көру»` заметно шире `«Попробовать бесплатно»` в узких местах,
а `«Қалай жұмыс істейді»` не влезает в навигацию на 1024px. **Любую правку
вёрстки проверять в KZ-локали**, там переполнение вылезает раньше.

### ⚠️ Шапка и авторизация: гидрация через `useHydrated`

Лендинг статический (`revalidate = 3600`) — серверный HTML печётся **без
сессии**, поэтому SSR всегда отдаёт гостевую шапку («Войти» / «Попробовать»).
Но `useAuth` через `initialData` **синхронно читает `sessionStorage`**: на
первом клиентском рендере залогиненного пользователя он уже возвращает
`isAuthenticated = true` → шапка рисует «Кабинет». Серверный HTML ≠ первый
клиентский → **recoverable hydration error** (React выкидывает поддерево и
перерисовывает).

Лечится `src/lib/useHydrated.ts` (на `useSyncExternalStore`, **не** `useEffect`
+ `setState` — тот падает на линте `react-hooks/set-state-in-effect`):
`getServerSnapshot` = `false`, `getSnapshot` = `true`. Шапка гейтит
`const authed = useHydrated() && isAuthenticated` — первый рендер совпадает с
сервером (гость), «Кабинет» появляется **после** гидрации. Клиентская
навигация `/ru ↔ /kz` (ремоунт дерева, без гидрации) отдаёт снапшот сразу
`true` — мигания в гостевую ветку нет. **Любую auth-зависимую разметку в
SSR-компонентах гейтить так же.**

## 8. Как проверять вёрстку

Не полагаться на чтение классов — брейкпоинты могут быть верными, а рендер
сломанным (см. §7). Проверять реальным браузером:

```js
// ставится разово: npm i -D playwright && npx playwright install chromium
// в package.json НЕ держим — postinstall качает 113MB на каждой сборке Vercel
const { chromium } = require("playwright");
const b = await chromium.launch();
const p = await b.newPage({ viewport: { width: 320, height: 900 } });
await p.goto("http://localhost:3000/", { waitUntil: "networkidle" });
// главный индикатор переполнения:
const sw = await p.evaluate(() => document.documentElement.scrollWidth);
// sw > width → горизонтальный скролл, вёрстка сломана
```

Контрольные ширины: **320, 360, 375, 414, 640, 768, 1024, 1280, 1440** —
и каждую в обеих локалях.

Чтобы найти виновника переполнения, обойти `document.querySelectorAll("body *")`
и собрать элементы, у которых `getBoundingClientRect().right > viewportWidth`.
Учесть, что элементы внутри контейнеров с `overflow-hidden` попадут в список
ложно — они обрезаны и скролл не создают.

## 10. Мультиязычность (i18n)

Язык — в URL: `/ru` и `/kz`. Это даёт SEO, ради которого всё и делалось: две
отдельные индексируемые страницы вместо одной, и ссылкой на казахскую версию
можно поделиться.

```
/            → 307 на /ru или /kz по заголовку Accept-Language
/ru          → русская версия (статика)
/kz          → казахская версия (статика)
/robots.txt  /sitemap.xml   ← вне локалей
```

### ⚠️ `kz` в адресе, но `kk` в разметке

`kz` — код **страны**, язык казахский — это `kk`. В URL оставлен привычный
`/kz`, но `<html lang>`, `hreflang` и `og:locale` отдают корректный `kk-KZ`,
иначе поисковики не распознают язык. Соответствие лежит в
`HTML_LANG` (`src/content/locales.ts`) — не «чинить» его на `kz`.

### Добавить новую локаль

1. `Locale` и объект копии в `src/content/landing.ts`
2. `LOCALES` и `HTML_LANG` в `src/content/locales.ts`
3. `languages` в `generateMetadata` (`app/[locale]/layout.tsx`) и в `sitemap.ts`
4. Определение языка в `proxy.ts`

### ⚠️ `siteUrl()` и canonical

`VERCEL_URL` уникален для **каждого деплоя** (`qr-front-a1b2c3.vercel.app`).
Если увести на него canonical, поисковик решит, что каждый деплой — отдельный
сайт. Поэтому порядок в `siteUrl()`:

```
NEXT_PUBLIC_SITE_URL          ← задать, когда появится свой домен
VERCEL_PROJECT_PRODUCTION_URL ← стабильный прод-домен (сейчас работает он)
VERCEL_URL                    ← только превью-деплои
localhost:3000
```

api.qr-menu.kz   → свой сервер (Laravel), HTTP 200
```

⚠️ **`qmenu.kz` — это больше НЕ наш лендинг.** Старый домен (см. журнал
2026-07-27) отдан под **демо тарифа Премиум**: на апексе живёт отдельный сайт-меню

после переезда (см. журнал 2026-08-07: «не трогаем до подтверждения»). Прежде чем
его гасить — проверить, что на него никто не ходит.

Схема одного домена второго уровня выбрана намеренно: Sanctum в SPA-режиме
работает на **куках**, а куки не ходят между чужими доменами. Будь фронт на
`*.vercel.app`, а API на `qmenu.kz` — это cross-site, куке потребовалась бы
`SameSite=None; Secure`, которую режет Safari ITP и добивает отказ Chrome от
сторонних кук, и админка начала бы разлогинивать пользователей. С общим
родителем `.qmenu.kz` кука `SameSite=Lax` работает штатно (проверено
end-to-end, см. журнал 2026-07-27).

Рабочая конфигурация, `backend/.env` на сервере (после переезда — на
`qr-menu.kz`, см. журнал 2026-08-07):

APP_URL=https://api.qr-menu.kz
SESSION_DOMAIN=.qr-menu.kz
SANCTUM_STATEFUL_DOMAINS=qr-menu.kz,www.qr-menu.kz
FRONTEND_URL=https://qr-menu.kz
```
В `config/cors.php`: `'supports_credentials' => true`.
Env-переменные Vercel: `NEXT_PUBLIC_API_URL=https://api.qr-menu.kz`,
`NEXT_PUBLIC_SITE_URL=https://qr-menu.kz`, `NEXT_PUBLIC_MENU_HOST=qr-menu.kz`
(это `NEXT_PUBLIC_*` — зашиты в бандл, меняются только редеплоем).
